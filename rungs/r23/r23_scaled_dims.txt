RUNG 23 scaled-config dims patch (applied by validate.sh to the oracle source to keep ONE source
of truth for the ~600 lines of proven lm10 machinery).

The orchestrator generates rungs/r23/out/r23_scaled_gen.rail by copying
rungs/r23/r23_segmented_train.rail and applying these exact substitutions in main:

  let hidden = 64 in        ->  let hidden = 256 in
  let epochs = 19 in        ->  let epochs = 120 in
  let seg_epochs = 5 in     ->  let seg_epochs = 20 in
  "tools/bitexact/lm10_corpus.txt"  ->  "rungs/r23/lm10_corpus_big.txt"

Rationale (per IMPL.md):
  * hidden=256 satisfies the gate's "hidden>=256" alternative; the readout MLP is dimension-generic
    (gpu_matvec / lm4_matvec_t read dims dynamically), so this stays Q.24 bit-exact.
  * epochs=120 + the 8-line corpus multiply transient garbage + canon body so a ONE-SHOT run needs
    far more peak arena than a SEGMENTED run that arena_resets every 20 epochs.
  * seg_epochs=20 over 120 epochs => nsegs = ceil(120/20) = 6 segments (>=4, the segmentation claim).
  * d and ctx are NOT scaled: the proven RoPE is hardcoded d=8/ctx=8 (rope_row reads 8 slots; the
    cos/sin tables are 8 positions x 4 pairs). A variable-d RoPE is a separate prerequisite.

NOTE the scaled config keeps the same transparency machinery, so it ALSO runs a one-shot oracle in
main. For a strict "does-not-fit" demonstration the orchestrator may instead run it under a TIGHT
arena (e.g. RAIL_ARENA_MB=2048): the segmented path survives (per-segment reset), the in-process
one-shot oracle path GC-thrashes/OOMs -> the one-shot==segmented equality is unprovable for this
config precisely BECAUSE it does not fit, which is the scaling claim. The oracle file already proves
the equality on the config that fits.
