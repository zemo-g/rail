### Phase 1 — parallelism + scale unlocks (today→tonight)

#### 1a. `compile.rail --out-prefix` flag [Studio / orchestrator]
**The single highest-leverage change this week.**

- Replace hardcoded `/tmp/rail_out.s` + `/tmp/rail_out` with CLI-overridable prefix.
- Grep for hardcoded paths: `grep -n "/tmp/rail_out" tools/compile.rail`
- Default stays `/tmp/rail_out` (self-compile path unaffected, backward compat).
- Usage: `./rail_native --out-prefix /tmp/w3_ file.rail` → `/tmp/w3_.s` + `/tmp/w3_`.
- Unlocks Stream 3's ≥4× oracle parallelism (today: 1.03×, bottlenecked here).
- Gate: `./rail_native self && cmp rail_native /tmp/rail_self` byte-identical.
- Estimate: 2–3 hours including the fixed-point gate iteration.

#### 1b. BPE open-addressed hash table finish [Stream 1 resumable]
- Diagnosis in `stdlib/bpe.rail:bpe_train_inc_wip` docblock (today's 694069e).
- Replace BST + `map_put` with open-addressed hash table (float_arr key/value
  pairs) + max-heap.
- Target: V=4096 on 540 KB in <5 min.
- Current: 466 s at 1.56 GB RSS (correct output, but arena-thrashing).
- Blocker, if any, will be Rail's 10-param helper wall + nullary-binding quirk
  (see `rail_quirks` memory).

#### 1c. T5 overnight run [Studio]
- `tools/train/lm_v3_chunked.rail` already has the unstaged wire-up
  (`seq_len=1024`, `corpus_path="training/rail_corpus_stdlib.txt"`).
- **Critical:** run in an isolated session — no other concurrent compile.rail
  work. Today's T5 attempt stalled at 14 min / 10.8 GB RSS specifically
  because three Mini sessions were hammering the compiler.
- Stage 10 → 50 → 500 steps; read each output before committing to longer.
- Command: `/usr/bin/time -l ./rail_native run tools/train/lm_v3_chunked.rail 2>&1 | tee /tmp/t5.log`
- Report peak memory footprint (NOT `ps` RSS; `time -l` is authoritative).
- Deliverable: loss curve + wall + `training/rail_native/T5_OVERNIGHT.md`.
- **Outcome (2026-04-20, 11183/12000 steps, 5h38m wall):** min loss 1.37
  @ step 1157 (not the 2.7–3.3 plateau). **d=64 is not capacity-bound** —
  that "plateau" is per-chunk eval variance, not a loss floor. Peak RSS
  35.84 GB (vs 437 MB at 500 steps — super-linear small-block leak).
  Cosine tail past step ~1550 produced no new min. See
  `training/rail_native/T5_OVERNIGHT.md`.

#### 1d. Eval discipline + memory instrumentation [post-T5, precondition for Phase 2]

**Why:** 1c exposed two latent issues that make naive Phase 2a meaningless:
(a) single-chunk loss spans 1.4–4+ per step, so d=64 vs d=128 cannot be
ranked from point-loss readings; (b) small-block bump-region RSS grows
from 437 MB → 35 GB in the back half of long runs. Both need fixing
before any width/depth comparison will produce trustable numbers.

- **1d.1 Multi-chunk eval in `lm_v3_chunked.rail`.** Held-out fixed-seed
  set of 10 chunks (offsets chosen once at startup, not per step).
  Every N=100 train steps, run forward-only on all 10, report mean +
  std. This is the ranking signal. Keep the per-step print as liveness.
- **1d.2 Periodic RSS snapshot.** Every 500 steps, shell out to
  `/usr/bin/ps -o rss= -p <pid>` or equivalent, append to a file. This
  is diagnostic, not `time -l`'s peak — we want the growth *curve*.
- **1d.3 Memory bisect run.** 2000 steps with 1d.1+1d.2 active. Plot RSS
  vs step. Identify where growth changes regime. Likely candidates:
  `arr_new` patterns inside `m_train_step`, accumulating arena-blocks
  not reached by `arena_reset`; or something in the chunked-sampler.
- **1d.4 Fix the leak.** Pending bisect result. If arena-small-block:
  add munmap path for the bump region too, mirroring `d24340c`. If
  training-loop: pull the allocating call out of the hot path.
- **1d.5 Validate.** Re-run 2000 steps instrumented. Target: peak RSS
  < 2 GB at 2000 steps (d=64×2-block). Multi-chunk eval curve is
  monotonically non-increasing (modulo small oscillation).
- **Deliverable:** updated `lm_v3_chunked.rail`, `training/rail_native/1d_memory_bisect.md`
  with leak localization + RSS-vs-step plot numbers.

### Phase 2 — scale step (days 2–3)

**Prerequisite**: 1a + 1b + **1d** shipped. 1c established that d=64 is
not capacity-bound (min 1.37); 1d provides the ranking signal to
actually tell if d=128 / 4-block helps.

#### 2a. Width up: d=64 → d=128, 2-block
- Single-line edit in `lm_v3_chunked.rail` (model dim).
- **Revised budget (post-1c):** **≤3000 steps** with multi-chunk eval
  from 1d. 1c showed the min-loss touch is always in the first ~1500
  steps under cosine-to-zero schedule; longer runs are cosine-tail
  waste. Run two: 3000-step and — only if 3000 hasn't exhausted — a
  followup 2000-step from warmup-restart.
- **Baseline to beat:** d=64×2-block 10-chunk eval mean @ step 1500
  (captured in 1d validation). **Not** the single-point 2.15 — that
  number was per-chunk lucky.
- Expected wall post-arena-fix + post-1d-leak-fix: ~10–15 min at 3000
  steps.

#### 2b. Depth up: 2-block → 4-block (conditional on 2a holding)
- Kaiming init (`init_scaled` with std=√(2/fan_in)) is already default for
  multi-block — see `init_matters` memory.
- Learnable RMSNorm γ: adopt `adam_lr_mult_gamma=0.3` from Phase 0 commit 2.
  Addresses γ bounce (run `924e0c5`, 1.59→1.78 at step 349→399).
- Pattern from `stdlib/optim.rail` docblock (call-site pre-multiply, no wrapper):
  ```rail
  let scaled_lr_gamma = base_lr * adam_lr_mult_gamma
  let _ = adam_update_raw w_gamma g_gamma st_gamma scaled_lr_gamma b1 b2 eps
  ```

## Rollback / kill switches

| Situation | Recovery |
|---|---|
| Self-compile broke after commit | Revert on Mini: `git revert HEAD && git push`; pull back |
| Staged changes need dropping | `git restore --staged path && git restore path` |
