# Repo Reorganization Plan — 2026-04-20

**Status:** proposed, awaiting kickoff approval per step
**Decision:** Path A — split the Rail monorepo into focused repos
**Driver:** clone size is ~11GB (training + flywheel), UAV code is in a public repo in violation of our "drone private" rule, site source is orphaned, `tools/` has sprawl.

---

## Target topology

| Repo | Visibility | Scope | Approx size |
|---|---|---|---|
| `zemo-g/rail` (existing) | **public, BSL 1.1** | compiler + stdlib + core tests + docs + fleet control plane source | ~15MB |
| `ledatic-empire/ledatic-site` (new) | public | site2030 source + Cloudflare Worker + deploy scripts | ~500KB |
| `ledatic-empire/rail-training` (new) | **private** | flywheel/, training/, LLM data pipeline, bench scripts | ~11GB (git LFS or shallow) |
| `ledatic-empire/zemog` (new) | **private** | UAV, AIGP, flight brain, MAVSDK glue | ~10MB |
| `ledatic-empire/fleet` (new, optional) | **private** | fleet_agent binaries, self-healer, plist/unit files, allowed_commands templates | ~1MB |

The `fleet` split is optional — fleet control plane _source_ (`stdlib/socket.rail`, `tools/fleet/fleet_agent_v3.rail`) belongs in rail since it's Rail code. Only node-specific _config_ (tokens, allowed_commands, deploy recipes) needs to be private. Simplest: keep fleet source in rail, put node config in `ledatic-empire/fleet-config` private repo. Revisit after the rest is done.

## Migration order

Urgency-ordered. Do not reorder without reason — #1 is time-sensitive.

### 1. UAV scrub — **DO FIRST (today)**

`tools/uav/` is in the public `zemo-g/rail` repo. Per `feedback_drone_private.md`, zero UAV/ZEMOG specifics should be public. It's been exposed since the directory was added.

**Options:**
- **A1. Delete + commit** (fast, imperfect): `git rm -rf tools/uav && commit && push`. Scope stays visible in history. Anyone who already cloned has the code; anyone who clones fresh doesn't.
- **A2. Filter-repo scrub + force-push** (complete, destructive): rewrites public history. Breaks existing tags v3.0.0 → v3.6.0 for anyone who has cloned. Forces everyone to re-clone.

**Recommendation: A1.** The code in `tools/uav/` is already out — force-rewriting history after the fact doesn't un-leak it but does break every downstream clone and every tagged release. A1 stops the bleeding immediately; history is a known cost. The alternative (A2) pretends we can unring the bell.

Before deleting, copy `tools/uav/` → `~/projects/zemog/` as the seed for the new private repo.

### 2. Extract site to `ledatic-site`

- Initialize new public repo `ledatic-empire/ledatic-site` (or similar — user picks org name).
- Seed with `tools/deploy/site2030/` + `tools/deploy/worker.js` + `tools/deploy/deploy_worker.sh` + `tools/deploy/cf_deploy.rail` (copy, then port from Rail to a shell-only deploy step if we want to fully decouple).
- Move `update_site.rail` + `update_site_data.py` too.
- Add a deploy script that pushes site2030/ files to KV directly (no more `gen_site.rail` intermediary).
- **Retire `gen_site.rail`** once site2030 is live in production. Keep `gen_mission_control.rail`, `gen_changelog.rail`, `gen_feed.rail`, `gen_plasma_landing.rail` — those still generate dynamic pages and stay in rail for now.
- `~/ledatic-site/` (the current output dir) becomes the clone of the new repo.

**Open question:** does `ledatic-site` need Rail as a build dep, or is it pure HTML/CSS/JS/GLSL now? From the shipped 2030 rebuild, it's pure static — no Rail needed for the 8 hand-rolled pages. Dynamic pages (mission control, changelog, plasma landing) stay Rail-generated in the rail repo.

### 3. Extract training data → `rail-training`

This is where the bulk lives (11GB).

- `flywheel/` + `training/` + `tools/train/` (except anything rail-compiler-side) → new private repo.
- Use **Git LFS for model weights** (`.weights`, `.npz`, `.safetensors`, checkpoint dirs) OR leave checkpoints out of git entirely and document how to regenerate / where they're stored (rsync to a backup disk, S3, etc.).
- The Rail stdlib modules (`autograd.rail`, `transformer.rail`, `optim.rail`, `bpe.rail`, `tokenizer.rail`, `checkpoint.rail`) stay in `zemo-g/rail/stdlib/` — they're the _library_. The _models_ and _datasets_ leave.

**After extract, shrink rail repo:**
- `git rm -rf flywheel/ training/` in rail, commit, push.
- Accept that history still carries the weight (same logic as A1 above).
- Fresh clones of zemo-g/rail go from ~11GB → ~300MB (just history baggage from past commits).
- If we later want a genuinely small clone: `git filter-repo` + force-push at a version bump (v4.0.0?). Tie it to a planned release, not retroactively.

### 4. Extract UAV/ZEMOG → `zemog` (already seeded in step 1)

- Create private `ledatic-empire/zemog`.
- Initialize from the `~/projects/zemog/` copy made in step 1.
- Add its own `CLAUDE.md` with ZEMOG-specific context (quat axis swap, V3 protocol, competition rules, hardware bench setup).
- Memory already has `zemog-hardware-bench.md`, `zemog-breakthrough.md`, `zemog-v3-protocol.md`, `aigp-competition.md`, `rail-on-drone-fc.md` — those all point here now.

### 5. Root + tree cleanup in `zemo-g/rail` (after 1-4)

Now the public repo is just compiler + stdlib + docs. Final sweep:

- Prune merged branches: `git branch -d track-b-xfn-type-infer track-c-wasm-stackmaps track-d-metal-pool track-e-checkpoint track-f-bpe-perf track-g-http-client` (track-h was released as v3.0.0).

### 6. CLAUDE.md + memory update

## Rollback

- Keep `~/projects/rail/` as-is on a backup branch (`backup/pre-reorg-2026-04-20`) before any deletions.
- Do not force-push `zemo-g/rail` during reorg. Step 1 (UAV rm) is a new commit, not a history rewrite.
- New private repos are cheap to delete if we decide the split was wrong.

---

## What this plan deliberately does NOT do

- **Does not rewrite zemo-g/rail history.** Tags v3.0.0–v3.6.0 are sacred; downstream clones should keep working.
- **Does not change the compiler, stdlib, or tests.** Pure file movement.
- **Does not touch `~/empire/`, `~/ledatic-clients/`, `~/.ledatic/dream/`, `~/ledatic-watch/`.** Those are already properly separated.
- **Does not split fleet control plane source** from stdlib/tools — fleet is a Rail application and stays with Rail.
